# misra - Agent Guide

Canonical instructions for AI coding agents. `CLAUDE.md` and `GEMINI.md` point here; edit this file only.

## Project

Daily batch pipeline that crawls career pages, keeps its history in Supabase, and emails job alerts. Runs on GitHub Actions; there is no server or API. The only UI is the static dashboard in `docs/`. SQLite (`data/jobs.db`) is only a scratch file that a run rebuilds from Supabase; it is not committed.

## Commands

- Install: `npm ci`, then `python3 -m venv .venv && .venv/bin/pip install -e '.[dev]'`
- Lint: `npm run lint` (ruff, ESLint, Stylelint, html-validate, markdownlint; no emoji and no em dash in any source file, except the lawyer's files for the em dash: `scripts/lint-text.mjs`)
- Typecheck: `npm run typecheck` (mypy, strict)
- Test: `npm run test`
- Coverage: `npm run test:coverage` (pytest, 100% line and branch coverage; mandatory on push and in CI)
- Run the pipeline: `.venv/bin/python sync_supabase.py --pull` (rebuilds `data/jobs.db` from Supabase; needs `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY`, or `touch data/jobs.db` for a local trial with an empty history, which the sync refuses: only a pulled file may be written back), then `.venv/bin/python run.py` and `.venv/bin/python build_dashboard.py` (see README; `send_digests.py` needs the Supabase and Resend secrets, so it runs in the daily workflow)

## Rules

- Never commit with `--no-verify`. Fix the cause when a hook fails.
- This repository uses GitHub issues for ticketing.
- Linters are strict (ruff, mypy, ESLint, Stylelint, html-validate, markdownlint). Do not weaken rules to pass.
- The files in `docs/` (`index.html`, `dashboard.css`, `dashboard.js`, `auth.js`, `report.js`, `digest.js`, `email.html`, `email.js`, `supabase.js`, `theme.js`, `jobs.json`, `jobs.jsonld`, `privacy.html`, `terms.html`, `security.html`, `about.html`, `contact.html`, `contact.js`, `favicon.svg`, `apple-touch-icon.png`, `google0e1aa15dbd543e2f.html`) are generated by `build_dashboard.py` from `templates/dashboard.html`, `templates/dashboard.js`, `templates/auth.js`, `templates/report.js`, `templates/digest.js`, `templates/email.html`, `templates/email.js`, `templates/contact.html`, `templates/contact.js`, `templates/theme.js`, `vendor/supabase.js` (copied unmodified, see `vendor/README.md`), `design-system/assets/mark.svg` (the favicon) and `design-system/assets/apple-touch-icon.png` (a 180 px render of the mark on white) and the data (`google0e1aa15dbd543e2f.html`, the Google Search Console ownership file, is `templates/google0e1aa15dbd543e2f.html` copied unchanged: it must stay served at that address for good, so never remove it; it is not HTML and `scripts/lint-html.mjs` skips it): edit the templates, never the output. `privacy.html`, `terms.html`, `security.html` and `about.html` (and `assistant.html`, only while `ASSISTANT_PAGE_ENABLED` is on) are the Markdown files `PRIVACY.md`, `TERMS.md`, `SECURITY.md`, `ABOUT.md` and `ASSISTANT.md` converted into `templates/legal.html` (markdown-it-py, pinned): the Markdown is the source of truth, so edit it and never the HTML, and link to the pages on the site (`https://ravidorr.github.io/misra/privacy.html`), not to the files on GitHub. `.github/workflows/publish-docs.yml` rebuilds `docs/` when one of those sources changes on `main`. `docs/dashboard.css` bundles `design-system/tokens.css`, `design-system/components/*.css` and `templates/dashboard.css`. The header and the footer of every page are written once in `templates/parts/` (`header.inc`, `footer.inc`; `account.inc` and `updated.inc` are slots only the dashboard fills) and put in by `build_dashboard.apply_chrome` at the `__HEADER__` and `__FOOTER__` of `dashboard.html`, `email.html` and `legal.html`: add a footer link in `footer.inc` only. The page has no inline script or style (its Content-Security-Policy forbids them); add integrity hashes through the `__SRI_*__` placeholders in the template.
- UI work follows `design-system/README.md`: tokens only (no raw colors outside `tokens.css`), kebab-case classes, light and dark, WCAG AA, 44px targets. Keep the dashboard agent-readable: `data-*` hooks on `article.card`, the JSON-LD in `jobs.jsonld`, and the WebMCP tools registered in `templates/dashboard.js`.
- Python lives at the repository root (flat modules). Node is dev tooling only (linters, hooks, release gate); pin it via `.nvmrc`, package manager is `npm`. Keep `package-lock.json` committed.
- Keep the version in `package.json` and `pyproject.toml` equal. PRs that change `package.json`, `pyproject.toml`, or a listed Python module update `CHANGELOG.md` and bump both (one SemVer bump per PR). Docs-only, test-only, and workflow-only PRs do not.
- When adding a Python module, add it to `RELEASE_TRIGGER_PATHS` in `.github/workflows/ci.yml` and `.husky/pre-push`, and to `py-modules` and mypy `files` in `pyproject.toml`; the release gate only watches that list.
- The history lives in Supabase (`jobs`, open and closed, and `crawl_log`; step 9.1), not in the repository. Every run starts with `sync_supabase.py --pull`, which rebuilds the scratch file `data/jobs.db` (never committed, git-ignored; no text of a posting in it) and refuses an empty `jobs` table (it marks the file with `PRAGMA user_version`, and the sync refuses an unmarked one: a history that did not come from Supabase would overwrite every `first_seen`); the crawl and the dashboard build refuse a missing file; the sync step writes the jobs and this run's `crawl_log` rows back and keeps 90 days of log. `run.py` still works on SQLite, so a new table needs its place in `common.SCHEMA` and in `sync_supabase.py`, never a second store. The "new" coverage gaps are read from `crawl_log`; the sync deletes the `jobs` of a company this run skipped for robots.txt (`delete_robots_skipped`), so nothing else has to be remembered between runs. The service-role key is exposed to the pull, sync, digests and backup steps of the daily workflow and the pull step of `publish-docs`, never to the crawl.
- The daily workflow commits only the built `docs/` files straight to `main` (never `data/`). The `publish-docs` workflow pushes the same way, with the same key, but only `docs/` and only after `sync_supabase.py --pull` and `build_dashboard.py` (no crawl); it shares the daily workflow's `concurrency` group so the two never push together. Both push with the `DEPLOY_KEY` secret (a write deploy key), written to disk only in the final push step by `scripts/deploy-key.sh`, never during the crawl; do not add `ssh-key:` to either checkout step. That key is the only actor allowed to push directly to `main` under the `protect-main` ruleset (the Actions bot cannot be a bypass actor on a personal repo); step 9.1 does not change that, since `docs/` is still pushed the same way. Do not change that flow without updating the ruleset.
- The job alerts signup (`templates/digest.js` and the parts of `templates/dashboard.html` between `<!--digest-->` and `<!--/digest-->`) is behind two switches: `DIGEST_SIGNUP_ENABLED` in `build_dashboard.py` (on since PLAN.md step 6.6, v0.31.0) and the function secret of the same name (set by the maintainer on opening day). Never set the build constant back to `False` once anyone has subscribed (it also removes "End job alerts"); to close signups unset the secret. `tests/test_legal_wording.py` requires the present-tense digest wording in `PRIVACY.md` while the constant is on. No WebMCP tool may turn job alerts on or send mail.
- The form of the Contact page (`templates/contact.js` and the parts of `templates/contact.html` between `<!--contactform-->` and `<!--/contactform-->`, with the Edge Function `supabase/functions/contact/`) is behind two switches: `CONTACT_FORM_ENABLED` in `build_dashboard.py` (`False`) and the function secret of the same name (the function answers 404 unless it is `true`). Nobody flips either before the lawyer has agreed (the TODO.md item lists what he must decide; `tests/test_legal_wording.py` pins the constant). With the form off the page still carries the GitHub, security and privacy routes. The maintainer's address is never written on the page or in the function: the destination is the function secret `CONTACT_TO`. The function stores nothing and never logs an address, an IP or a message; it never emails the visitor.
- The assistant endpoint (`supabase/functions/mcp/`, PLAN.md step 8.1) can return the full text of one posting (`get_job`), so it is behind a switch: it answers 404 unless the function secret `ASSISTANT_ENDPOINT_ENABLED` is `true` (on since the lawyer approved it, 2026-11-17; to close it, unset the secret). The page that points to it (`ASSISTANT_PAGE_ENABLED` in `build_dashboard.py`, step 8.2, with `llms.txt`) is `True`; set it back to `False` together with unsetting the secret. Its wording (`ASSISTANT.md`, `TERMS.md`, `PRIVACY.md`) is the lawyer's: do not change it without him. It never returns the text in bulk, never reads user data, and never logs an address.
- The account tables and the job history (`jobs` without the text of the postings, and `crawl_log`; Supabase is their only home) are backed up every day to a private repository (`ravidorr/misra-backups`) by the `backup` step of the daily workflow: `export_accounts.py`, then `publish_backup.py` (history replaced after 28 days, so deletions are honoured within 30). This repository is public: account data is never committed here, logged (counts only), uploaded as an artifact or written inside the checkout, and the text of a posting is never in the export. `BACKUP_DEPLOY_KEY` and the service-role key are exposed to that step only; do not give any checkout an `ssh-key:`. Restore with `restore_accounts.py` (`CONTRIBUTING.md`, "Backups of the account tables"). A new account table or column goes into `TABLES` in `export_accounts.py`, a new `jobs` or `crawl_log` column into `JOBS`/`CRAWL_LOG` (text columns excepted); a test checks them against the migrations.
- `data/companies.json` is the one list of every company; nothing about a company lives anywhere else (no seed list, override file, link file or research output). `crawl: true` is the only thing that makes the pipeline request a site, and `discover.py` rewrites only the discovered fields of those records. Edit it by hand for everything else (`CONTRIBUTING.md`, "Adding a company"). `tests/test_companies_data.py` checks it. The exclusion list `data/excluded_companies.csv` stays a separate list on purpose: it is a legal opt-out with its own guards.

## Layout

- Python modules at the root (`run.py`, `adapters.py`, `browser_crawl.py`, `classify.py`, `regions.py`, `send_digests.py`, `sync_supabase.py`, `export_accounts.py`, `publish_backup.py`, `restore_accounts.py`, `build_dashboard.py`, `discover.py`, `common.py`, `descriptions.py`, dev tools `survey*.py`), `tests/` for pytest
- `data/` - `companies.json`, the one list of every company, crawled or researched (the history is in Supabase; `data/jobs.db` is a git-ignored scratch file); `templates/` - dashboard page, script and styles; `docs/` - generated dashboard (GitHub Pages)
- `design-system/` - tokens, components, showcase page (`index.html`), logo brief; `templates/dashboard.css` - dashboard layout
- `supabase/` - migrations, policy tests and Edge Functions (`functions/`, TypeScript for Deno; logic in plain modules tested by vitest in `test/`, type-checked by `test/typecheck-functions.test.mjs`); `vendor/` - unmodified third-party scripts (supabase-js)
- `.husky/` - git hooks (pre-commit fast, pre-push broad)
- `.github/` - CI, release, daily pipeline, dependabot, templates
