# misra - Agent Guide

Canonical instructions for AI coding agents. `CLAUDE.md` and `GEMINI.md` point here; edit this file only.

## Project

Daily batch pipeline that crawls career pages, keeps its history in Supabase, and emails job alerts. Runs on GitHub Actions; there is no server or API. The only UI is the static dashboard in `docs/`. SQLite (`data/jobs.db`) is only a scratch file that a run rebuilds from Supabase; it is not committed.

## Commands

- Install: `npm ci`, then `python3 -m venv .venv && .venv/bin/pip install -e '.[dev]'`
- Lint: `npm run lint` (ruff, ESLint, Stylelint, html-validate, markdownlint; no emoji and no em dash in any source file, the lawyer's files included: `scripts/lint-text.mjs`)
- Typecheck: `npm run typecheck` (mypy, strict)
- Test: `npm run test`
- Coverage: `npm run test:coverage` (pytest, 100% line and branch coverage; mandatory on push and in CI)
- Run the pipeline: `.venv/bin/python sync_supabase.py --pull` (rebuilds `data/jobs.db` and `data/companies.json` from Supabase; needs `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY`, or `mkdir -p data && touch data/jobs.db && cp tests/fixtures/companies.json data/companies.json` for a local trial with an empty history and a frozen list, which the sync refuses: only a pulled history may be written back), then `.venv/bin/python run.py` and `.venv/bin/python build_dashboard.py` (see README; `send_digests.py` needs the Supabase and Resend secrets, so it runs in the daily workflow)

## Rules

- Never commit with `--no-verify`. Fix the cause when a hook fails.
- This repository uses GitHub issues for ticketing.
- Linters are strict (ruff, mypy, ESLint, Stylelint, html-validate, markdownlint). Do not weaken rules to pass.
- The files in `docs/` (`index.html`, `dashboard.css`, `dashboard.js`, `auth.js`, `session.js`, `report.js`, `digest.js`, `email.html`, `email.js`, `supabase.js`, `theme.js`, `jobs.json`, `jobs.jsonld`, `privacy.html`, `terms.html`, `security.html`, `about.html`, `contact.html`, `contact.js`, `admin.html`, `admin.js`, `404.html`, `favicon.svg`, `new-tab.svg`, `apple-touch-icon.png`, `google0e1aa15dbd543e2f.html`) are generated by `build_dashboard.py` from `templates/dashboard.html`, `templates/dashboard.js`, `templates/auth.js`, `templates/session.js`, `templates/report.js`, `templates/digest.js`, `templates/email.html`, `templates/email.js`, `templates/contact.html`, `templates/contact.js`, `templates/admin.html`, `templates/admin.js`, `templates/not-found.html`, `templates/theme.js`, `vendor/supabase.js` (copied unmodified, see `vendor/README.md`), `design-system/assets/mark.svg` (the favicon), `design-system/assets/new-tab.svg` (the mask of the "opens in a new tab" icon, see `design-system/components/external-link.css`) and `design-system/assets/apple-touch-icon.png` (a 180 px render of the mark on white) and the data (`google0e1aa15dbd543e2f.html`, the Google Search Console ownership file, is `templates/google0e1aa15dbd543e2f.html` copied unchanged: it must stay served at that address for good, so never remove it; it is not HTML and `scripts/lint-html.mjs` skips it): edit the templates, never the output. `privacy.html`, `terms.html`, `security.html` and `about.html` (and `assistant.html`, only while `ASSISTANT_PAGE_ENABLED` is on) are the Markdown files `PRIVACY.md`, `TERMS.md`, `SECURITY.md`, `ABOUT.md` and `ASSISTANT.md` converted into `templates/legal.html` (markdown-it-py, pinned): the Markdown is the source of truth, so edit it and never the HTML, and link to the pages on the site (`https://ravidorr.github.io/misra/privacy.html`), not to the files on GitHub. `.github/workflows/publish-docs.yml` rebuilds `docs/` when one of those sources changes on `main`. `docs/404.html` is the 404 page GitHub Pages serves for a missing address at any depth, so `build_dashboard.py` makes its links and assets absolute under `SITE_PATH` (`/misra/`); it is `noindex`, never linked and not in `llms.txt` or `jobs.jsonld`. `docs/dashboard.css` bundles `design-system/tokens.css`, `design-system/components/*.css` and `templates/dashboard.css`. The header and the footer of every page are written once in `templates/parts/` (`header.inc`, `footer.inc`; `account.inc` and `updated.inc` are slots only the dashboard fills; `not-found.inc` is the words of the 404) and put in by `build_dashboard.apply_chrome` at the `__HEADER__` and `__FOOTER__` of `dashboard.html`, `email.html` and `legal.html` (and the `__NOT_FOUND__` of `admin.html` and `not-found.html`): add a footer link in `footer.inc` only. The page has no inline script or style (its Content-Security-Policy forbids them); add integrity hashes through the `__SRI_*__` placeholders in the template.
- UI work follows `design-system/README.md`: tokens only (no raw colors outside `tokens.css`), kebab-case classes, light and dark, WCAG AA, 44px targets. Keep the dashboard agent-readable: `data-*` hooks on `article.card`, the JSON-LD in `jobs.jsonld`, and the WebMCP tools registered in `templates/dashboard.js`.
- Python lives at the repository root (flat modules). Node is dev tooling only (linters, hooks, release gate); pin it via `.nvmrc`, package manager is `npm`. Keep `package-lock.json` committed.
- Keep the version in `package.json` and `pyproject.toml` equal. PRs that change `package.json` (beyond its `devDependencies`, so Dependabot's dev tooling bumps need no release), `pyproject.toml`, or a listed Python module update `CHANGELOG.md` and bump both (one SemVer bump per PR). Docs-only, test-only, and workflow-only PRs do not.
- When adding a Python module, add it to `RELEASE_TRIGGER_PATHS` in `.github/workflows/ci.yml` and `.husky/pre-push`, and to `py-modules` and mypy `files` in `pyproject.toml`; the release gate only watches that list.
- The history lives in Supabase (`jobs`, open and closed, and `crawl_log`; step 9.1), not in the repository. Every run starts with `sync_supabase.py --pull`, which also writes the company list (below) and rebuilds the scratch file `data/jobs.db` (never committed, git-ignored; no text of a posting in it) and refuses an empty `jobs` table (it marks the file with `PRAGMA user_version`, and the sync refuses an unmarked one: a history that did not come from Supabase would overwrite every `first_seen`); the crawl and the dashboard build refuse a missing file; the sync step writes the jobs and this run's `crawl_log` rows back and keeps 90 days of log. `run.py` still works on SQLite, so a new table needs its place in `common.SCHEMA` and in `sync_supabase.py`, never a second store. The "new" coverage gaps are read from `crawl_log`; the sync deletes the `jobs` of a company this run skipped for robots.txt (`delete_robots_skipped`), so nothing else has to be remembered between runs. The service-role key is exposed to the pull, sync, digests and backup steps of the daily workflow, the pull step of `publish-docs`, and the pull and the final push steps of the manual `discover-companies` workflow (`discover.py` runs in a step between them without the key, and nothing there pushes to the repository), never to the crawl or to `discover.py`.
- The daily workflow commits only the built `docs/` files straight to `main` (never `data/`). The `publish-docs` workflow pushes the same way, with the same key, but only `docs/` and only after `sync_supabase.py --pull` and `build_dashboard.py` (no crawl); it shares the daily workflow's `concurrency` group so the two never push together. Both push with the `DEPLOY_KEY` secret (a write deploy key), written to disk only in the final push step by `scripts/deploy-key.sh`, never during the crawl; do not add `ssh-key:` to either checkout step. That key is the only actor allowed to push directly to `main` under the `protect-main` ruleset (the Actions bot cannot be a bypass actor on a personal repo); step 9.1 does not change that, since `docs/` is still pushed the same way. Do not change that flow without updating the ruleset.
- The job alerts signup (`templates/digest.js` and the parts of `templates/dashboard.html` between `<!--digest-->` and `<!--/digest-->`) is behind two switches: `DIGEST_SIGNUP_ENABLED` in `build_dashboard.py` (on since PLAN.md step 6.6, v0.31.0) and the function secret of the same name (set by the maintainer on opening day). Never set the build constant back to `False` once anyone has subscribed (it also removes "End job alerts"); to close signups unset the secret. `tests/test_legal_wording.py` requires the present-tense digest wording in `PRIVACY.md` while the constant is on. No WebMCP tool may turn job alerts on or send mail.
- The form of the Contact page (`templates/contact.js` and the parts of `templates/contact.html` between `<!--contactform-->` and `<!--/contactform-->`, with the Edge Function `supabase/functions/contact/`) is behind two switches: `CONTACT_FORM_ENABLED` in `build_dashboard.py` (`True` since the lawyer's wording of 2026-11-18, round 12; `tests/test_legal_wording.py` pins it and his `PRIVACY.md` bullet) and the function secret of the same name (the function answers 404 unless it is `true`). To close the form unset the secret, then set the constant back to `False`; with the form off the page only points to the privacy notice (its address). The maintainer's address is never written on the page or in the function: the destination is the function secret `CONTACT_TO`. The function stores nothing and never logs an address, an IP or a message; it never emails the visitor.
- The admin page (`templates/admin.html`, `templates/admin.js`) is `noindex` and is never linked from a page, the footer, `llms.txt` or `jobs.jsonld`, and no WebMCP tool touches it (a test checks each). It has no sign-in of its own: the sign-in stays on the dashboard, and `templates/session.js` (the storage key and the wrapper that strips the provider's name and photo from the saved session) is the one piece `auth.js` and `admin.js` share. To anyone who is not an admin (signed out, signed in without the role, or without JavaScript) `admin.html` shows the 404 page as its default markup, and `admin.js` swaps in the admin page only after `is_admin()` is true; a signed-in visitor whose check fails sees one neutral line. GitHub Pages cannot answer a real HTTP 404 for it and hiding adds no security (this script is public): the page has no power of its own, the database (row-level security and `is_admin()`) decides, never this script.
- The assistant endpoint (`supabase/functions/mcp/`, PLAN.md step 8.1) can return the full text of one posting (`get_job`), so it is behind a switch: it answers 404 unless the function secret `ASSISTANT_ENDPOINT_ENABLED` is `true` (on since the lawyer approved it, 2026-11-17; to close it, unset the secret). The page that points to it (`ASSISTANT_PAGE_ENABLED` in `build_dashboard.py`, step 8.2, with `llms.txt`) is `True`; set it back to `False` together with unsetting the secret. Its wording (`ASSISTANT.md`, `TERMS.md`, `PRIVACY.md`) is the lawyer's: do not change it without him. It never returns the text in bulk, never reads user data, and never logs an address.
- The account tables, the job history (`jobs` without the text of the postings, and `crawl_log`) and the company list (`companies`, the excluded records included; Supabase is their only home) are backed up every day to a private repository (`ravidorr/misra-backups`) by the `backup` step of the daily workflow: `export_accounts.py`, then `publish_backup.py` (history replaced after 28 days, so deletions are honoured within 30). This repository is public: account data is never committed here, logged (counts only), uploaded as an artifact or written inside the checkout, and the text of a posting is never in the export. `BACKUP_DEPLOY_KEY` and the service-role key are exposed to that step only; do not give any checkout an `ssh-key:`. Each snapshot holds every current record, so the squash of the history never loses an exclusion; an exclusion removed on purpose leaves the backup within the same 30 days. Restore with `restore_accounts.py` (`CONTRIBUTING.md`, "Backups of the account tables"); it is also how an empty `companies` table is refilled (the script refuses a non-empty `companies`, so empty it first: a seeded row would win over the backup and hide an exclusion, `CONTRIBUTING.md`, Restore step 3). A new account table or column goes into `TABLES` in `export_accounts.py`, a new `jobs`, `crawl_log` or `companies` column into `JOBS`/`CRAWL_LOG`/`COMPANIES` (text columns excepted); a test checks them against the migrations (`admins`, one hand-inserted row with no personal data, is left out on purpose).
- The Supabase table `companies` is the one list of every company (PLAN_2.md step 3): the crawled ones, the researched ones (`gap`) and the excluded ones (`excluded: {reason, date_added}`, a record that holds the name, `crawl: false` and nothing else, the legal opt-out with its own guards in `common.load_excluded`); nothing about a company lives anywhere else (no seed list, override file, link file, exclusion file or research output). The rules of a record are the database checks of `supabase/migrations`, not Python. `sync_supabase.py --pull` writes the git-ignored scratch file `data/companies.json` from the table (every row, the excluded ones included; an empty table, or one with fewer than half of the baseline's records or of `covered` in `docs/jobs.json`, is refused), as it writes `data/jobs.db`; `run.py`, `build_dashboard.py`, `discover.py` and the sync read that file and never the table. `crawl: true` is the only thing that makes the pipeline request a site, with one exception the maintainer decided on 2026-11-21: the daily recheck (`run.py --recheck`) reads, and only reads, the researched records whose gap reason is `no_openings` or `crawl_failing` and that have a `careers_url`, under the same `robots.txt` and one-request-a-second rules, writing nothing (no history, no table); every other researched record, and every excluded one, is never requested. The `discover-companies` workflow runs `discover.py --new-only`: only the crawled records with an empty `status` are discovered and every other record stays as pulled (a runner IP cannot rebuild the whole list; a full re-discovery is `discover.py` by hand). `discover.py` rewrites only the discovered fields (`discover.DISCOVERED`) of those records, and `sync_supabase.py --push-companies` sends back only those fields, for the records it changed, never a field a person owns (`crawl`, `gap`, `excluded`, `links`). Edit the list on the Companies area of the admin page, which writes through the admin's session (row-level security and the table's checks decide, never the page, and never a service-role key), or the table for what the page does not edit (`CONTRIBUTING.md`, "Adding a company"). The page never removes an excluded record (the opt-out persists), shows each refused write as one plain sentence from a map in `templates/admin.js` that a test keeps equal to the migration's constraint names, and never shows the database's error text, which can quote a row. Tests read the frozen copy `tests/fixtures/companies.json`, never a live list.
- Agents implement and open the PR; the coordinator merges. The brief, the PR cycle, the company-list rules and the stop conditions are in `CONTRIBUTING.md`, "Working with agents" (and the `misra-pr` skill).

## Layout

- Python modules at the root (`run.py`, `adapters.py`, `browser_crawl.py`, `classify.py`, `regions.py`, `send_digests.py`, `sync_supabase.py`, `export_accounts.py`, `publish_backup.py`, `restore_accounts.py`, `build_dashboard.py`, `discover.py`, `common.py`, `descriptions.py`, dev tools `survey*.py`), `tests/` for pytest
- `data/` - not in git: the pull creates it and writes the git-ignored scratch files `data/jobs.db` (the history) and `data/companies.json` (the company list), both from Supabase; `templates/` - dashboard page, script and styles; `docs/` - generated dashboard (GitHub Pages)
- `design-system/` - tokens, components, showcase page (`index.html`), logo brief; `templates/dashboard.css` - dashboard layout
- `supabase/` - migrations, policy tests and Edge Functions (`functions/`, TypeScript for Deno; logic in plain modules tested by vitest in `test/`, type-checked by `test/typecheck-functions.test.mjs`); `vendor/` - unmodified third-party scripts (supabase-js)
- `.husky/` - git hooks (pre-commit fast, pre-push broad)
- `.github/` - CI, release, daily pipeline, dependabot, templates
