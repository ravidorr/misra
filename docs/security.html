Do not open a public issue. Report vulnerabilities privately through GitHub private vulnerability reporting (Security tab, then Report a vulnerability). If that is unavailable, email raanan@avidor.org. Expect an acknowledgement within 3 business days.

How Misra protects its data

Written 2026-11-15 by the maintainer, Raanan Avidor. Next full review due by 2027-11-15. This is the short security note that the Israeli Data Security Regulations (2017) expect for a database at the "basic" level (a computerised database of email addresses of people outside the owner's own circle). It is public on purpose: the repository is public and so are the rules that protect the data.

What the database holds

  • The email address of each person who signs in with Google, their stars, their "Not for me" choices and their saved filters. When the daily email exists: the address it goes to, the filters copied for it, daily or weekly, and a consent log (when it was turned on, confirmed and unsubscribed).
  • Never a CV, a phone number, a postal address or a password. Google's name and photo sit only in Supabase's own sign-in record until the account is deleted. The jobs data is public job postings.
  • Where it lives: Supabase (EU, Ireland) for the database, sign-in and Edge Functions; Resend (Ireland) for email; Google for sign-in; GitHub for the repository, the dashboard and the daily job. One maintainer runs all of them.

Controls in place

  • Access to rows: row-level security on every table. A signed-in person can read and change only their own rows, and the public (anon) key can read open jobs only. The policy tests are in supabase/tests/.
  • Secrets: the service-role key lives only in Supabase's function settings and in GitHub Actions secrets, never in the browser or the repository. Other secrets by name: RESEND_API_KEY (limited to sending from send.avidor.org), REPORT_TO_EMAIL, IP_HASH_SECRET and the GitHub deploy key. Values are typed into the providers' own pages.
  • Accounts: two-factor sign-in is on for Supabase, GitHub, Resend and Google. Users sign in with Google only: the email-and-password provider is switched off. A database hook empties the personal part of the sign-in token.
  • Policy tests: the SQL policy tests of supabase/tests run in CI on every pull request and push to main, against a plain Postgres 17 database with a stub of Supabase's roles and auth schema. They are the real tests of the row-level security; a stub is not a Supabase project, so the live checks in supabase/README.md still apply.
  • Abuse limits: the report form has a honeypot, a per-visitor daily limit and a daily cap; the email functions have per-user, per-address and daily limits.
  • Deletion: a person can delete their account in one step, and every row tied to it is removed at once.
  • Transport: all traffic is HTTPS, and the page's security policy only allows connections to its own files and to the Supabase project.

Known gaps (accepted for now)

  • Supabase's free plan has no backups. Before the first daily-email subscriber, upgrade to a plan with backups or build the export in plan step 9.1.
  • Two low-risk Dependabot alerts in development tools (not shipped to users) were open on 2026-11-15.
  • One maintainer: no second person for access or recovery.

Yearly review (by 2027-11-15, then every year)

  1. Read Supabase's auth and API logs for odd sign-ins or request patterns.
  2. List who has access to the Supabase organisation, the GitHub repository (collaborators, deploy keys, tokens) and the Resend team, and remove anyone or anything not needed.
  3. Confirm two-factor sign-in is still on for all four providers.
  4. Rotate the service-role key and the Resend key, and update the secrets.
  5. Check Dependabot and CodeQL alerts and update dependencies.
  6. Re-read PRIVACY.md and TERMS.md against what the product really does.

Reviews done: none yet.

If there is a breach

  1. Contain it: rotate the service-role key and any exposed secret, disable the affected Edge Function or sign-in provider, and fix the hole.
  2. Find out what was exposed: which tables, which people, since when (use the provider logs).
  3. Tell the affected people by a short, plain email: what was exposed (their email address and saved choices, for example), what was done, and how to delete their account. No report to the regulator is required at this level, but telling the people is the right thing to do.
  4. Write it down: the date, what happened and what was changed. If the database ever grows past the basic level (sensitive data, or a very large number of people), ask a lawyer again whether a report to the authority is required.
